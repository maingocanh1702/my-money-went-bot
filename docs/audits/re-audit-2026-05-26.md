## New Findings

### [P0] Durable ref reservation can permanently drop a real transaction after append failure

- **Evidence:** `tx_exists()` reserves a ref before processing at `sheets.py:545-556`. `handle_sepay_webhook()` then appends the transaction and only afterwards marks the ref committed at `handlers/sepay.py:137-145` and `handlers/sepay.py:178-185`. `_ref_in_processed_refs()` treats any existing ref row, including `"reserved"`, as already processed at `sheets.py:493-506`.
- **Impact:** If `append_transaction()` or a later write fails after the reservation succeeds but before `mark_ref_committed()`, a SePay retry with the same real ref will be skipped as a duplicate. That changes the prior duplicate-risk fix into a money-loss/data-loss failure mode.
- **Priority:** P0 because a real bank transaction can be silently absent from the Transactions sheet after retry.
- **Suggested fix:** Make reservation and transaction append recoverable as a state machine: distinguish `reserved`, `processing`, `committed`, and `failed/stale`, include age-based retry of stale reservations, and only suppress retries for committed refs. Prefer a backing store with uniqueness/transaction semantics if possible.

### [P2] Security documentation is stale and contradicts the fixed behavior

- **Evidence:** README still says webhook auth is opt-in and that an unset `SEPAY_SECRET` lets callers spam fake transactions at `README.md:308`; Vietnamese README repeats the same claim at `README.vi.md:308`. Current config says the bot exits in non-test mode when `SEPAY_SECRET`, `TELEGRAM_WEBHOOK_SECRET`, or `CRON_SECRET` is missing at `config.py:28-42`.
- **Impact:** Operators may follow stale deployment guidance or misunderstand that the new secrets are mandatory.
- **Priority:** P2 documentation/deployment correctness.
- **Suggested fix:** Update both READMEs to describe the mandatory startup requirements and the Telegram webhook secret header setup.

## Regression Notes

- The webhook security fix is code-level credible, but route-level Telegram auth coverage is incomplete because the relevant test bypasses `/webhook` and calls `_process` directly (`tests/unit/test_webhook_auth.py:97-119`).
- The added CI workflow runs Ruff (`.github/workflows/ci.yml:33-34`), but local Ruff was not installed, so this audit could not confirm the new CI lint gate passes.
- README security claims are now inconsistent with the implementation, as noted above.

## Final Recommendation

**Not safe to deploy yet.** The public-auth P0s are fixed, but the idempotency remediation introduces a P0 money correctness regression: a ref reserved before a failed append can cause real SePay retries to be ignored permanently. Fix and test that retry/recovery path before deploying.
