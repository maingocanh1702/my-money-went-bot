## Severity Rubric

- **P0:** money loss/corruption, unauthenticated control of the bot, secret exposure, or silent data integrity failure.
- **P1:** exploitable-but-bounded, correctness bug under realistic conditions, or a structural issue that will cause a P0 soon.
- **P2:** maintainability, missing tests, code smells, non-exploitable hardening.

## Executive Summary

The highest-risk issue is authentication: the public `/webhook` endpoint trusts any JSON body that looks like a Telegram update or SePay webhook. A caller who knows the Railway URL can drive owner-scoped commands/state and can inject fake bank transactions when `SEPAY_SECRET` is unset.

Money correctness is mostly protected by sheet-backed ref-code lookup and ledger flags, but duplicate delivery is still race-prone across workers/restarts or sheet read failures, and all money math uses `float`.

The codebase has useful unit coverage for sheet/ledger/account/report behavior, but the risky public boundary has no tests, `tests/integration/` is empty, and there is no CI/lint/type gate.

## Findings

### [P0] Public webhook accepts forged Telegram updates as the owner

- **Lens:** Security
- **Location:** `main.py:90-143`
- **Evidence:**
  ```python
  async def _process(body: dict):
      try:
          # --- Telegram update ---
          if "update_id" in body:
              if "callback_query" in body:
                  await _handle_callback(body["callback_query"])
              elif "message" in body:
                  await _handle_message(body["message"])
          # --- SePay webhook ---
          else:
              await handle_sepay_webhook(body)
  ...
  async def _handle_message(message: dict):
      if message.get("from", {}).get("is_bot"):
          return
  
      text  = (message.get("text") or "").strip()
      state = sh.get_state(CHAT_ID) or {}
  
      # Commands take priority
      if text.startswith("/"):
          await _handle_command(text)
  ```
- **Impact:** Any internet caller who can reach `/webhook` can POST a fake Telegram-shaped body with `"update_id"` and command text. The handler does not verify Telegram's webhook secret header, `message.chat.id`, or `message.from.id` against `CHAT_ID`, then reads/writes owner state using the global `CHAT_ID`. This is unauthenticated control of bot workflows.
- **Recommended fix:** Configure Telegram webhook with a secret token and require `X-Telegram-Bot-Api-Secret-Token` in `webhook()` before dispatch. In `_handle_message()` and `_handle_callback()`, reject updates whose chat/user id does not exactly match `CHAT_ID`.
- **Effort:** M

### [P0] SePay webhook authentication is optional and defaults open

- **Lens:** Security
- **Location:** `config.py:18-20`, `handlers/sepay.py:36-48`
- **Evidence:**
  ```python
  # Optional: SePay webhook secret — nếu set, bot sẽ reject webhook không khớp token
  SEPAY_SECRET = os.environ.get("SEPAY_SECRET", "")
  ```
  ```python
  async def handle_sepay_webhook(payload: dict):
      # Optional: validate SePay webhook secret
      if SEPAY_SECRET:
          incoming_secret = (
              payload.get("apikey")
              or payload.get("token")
              or payload.get("secret")
              or (payload.get("data") or {}).get("apikey")
          )
          if incoming_secret != SEPAY_SECRET:
              print(f"[sepay] rejected: invalid secret")
              return
  ```
- **Impact:** With the default empty `SEPAY_SECRET`, any non-Telegram-shaped JSON sent to the public `/webhook` is processed as a bank webhook. A forged payload can write fake income/expense rows, trigger Telegram prompts, and corrupt reports/balances.
- **Recommended fix:** Make `SEPAY_SECRET` required at startup for deployed environments and fail closed if missing. Validate the SePay token before scheduling background work, preferably from a documented header/body field using constant-time comparison.
- **Effort:** S

- **Lens:** Money
- **Location:** `sheets.py:478-526`, `sheets.py:566-600`
- **Evidence:**
  ```python
  _processed_refs: dict[str, float] = {}  # ref_code → timestamp
  ...

      _processed_refs[ref_code] = now
      return True
  ```


  ```python

  ...
  ws.update(f"A{next_row}:U{next_row}", [row_data])
  ```
- **Impact:** The in-memory reservation is per process and the durable sheet lookup is fail-open. Two workers/restarts handling the same retry can both observe "not present" before either writes, and a transient sheet read failure returns `False`; both paths can append duplicate rows and double-count a real transaction.
- **Recommended fix:** Move idempotency to a durable, atomic-ish reservation layer: e.g. a dedicated `Processed Refs` tab with append-before-processing plus conflict check/retry, or a database/Redis uniqueness key. Treat sheet lookup failures as retryable failures instead of "not duplicate."

- **Lens:** Security
- **Location:** `main.py:107-131`, `handlers/allocation.py:197-199`, `handlers/manage.py:56-58`
- **Evidence:**

  ```python
  async def _handle_callback(cb: dict):
  ```


- **Impact:** A forged or malformed callback body can raise `KeyError`, `IndexError`, or `ValueError` before the handler validates shape. Today this is made worse by the unauthenticated webhook; after auth, it remains a robustness gap for stale/corrupt Telegram callback data.
- **Recommended fix:** Add a single callback parser/validator that checks required keys, prefix, minimum part count, numeric fields, and allowed actions before dispatch. Answer invalid callbacks with a generic notice and do not call downstream handlers.
- **Effort:** M

### [P2] Broad exception handler sends raw exception text to Telegram

- **Lens:** Security
- **Location:** `main.py:101-104`
- **Evidence:**
  ```python
  except Exception as e:
      import traceback
      print("ERROR:", traceback.format_exc())
      await tg.send_text(f"⚠️ Bot gặp lỗi: `{e}`")
  ```
- **Impact:** Exceptions raised while processing untrusted webhook input are rendered into an owner-visible Telegram message. This can leak internal row IDs, parser details, account identifiers, or library errors, and it gives attackers a cheap spam path while the public webhook remains unauthenticated.
- **Recommended fix:** Send a generic owner alert with a correlation id; keep full traceback in structured server logs with payload fields redacted. Rate-limit repeated failure notifications.

- The remaining risk is concurrent/restart/fail-open duplicate delivery, not ordinary sequential retry.

## Remediation Checklist

1. Require Telegram webhook secret header and exact `CHAT_ID`/sender validation before processing Telegram updates.
2. Require SePay secret in deployed environments and reject missing/invalid tokens before background dispatch.
3. Protect `/trigger/*` with a cron secret or internal scheduler.
4. Replace fail-open, process-local idempotency with durable duplicate prevention and retry behavior.
5. Convert money representation from `float` to integer minor units/`Decimal`.
6. Add callback schema validation before handler dispatch.
7. Replace raw exception Telegram messages with generic alerts and redacted logs.
8. Split `sheets.py` into repository modules and remove private `_sheet` usage from handlers.
9. Remove or explicitly isolate dormant `/transfer` and `/cc pay` code.
10. Add route/security/concurrency tests plus CI with pytest, Ruff, and type checking.
