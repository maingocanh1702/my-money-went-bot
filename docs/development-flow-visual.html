0Đầu tiên — hình dung quy trình

Cách dễ hình dung nhất

Tưởng tượng dự án là 1 cuốn sách đang được nhiều người viết cùng lúc. Cuốn sách đang bán ngoài hiệu sách không ai dám sửa thẳng vào. Mỗi khi muốn thêm chương, sửa lỗi, viết lại đoạn — phải viết bản nháp riêng, gửi biên tập viên duyệt, có người soát lỗi tự động, rồi mới đưa vào lần in tiếp theo.

Git và các khái niệm xoay quanh chính là hệ thống quản lý cái quy trình "nháp → duyệt → xuất bản" — nhưng cho code thay vì văn bản.

1Tám khái niệm cơ bản

Hiểu 8 khái niệm này là đủ để theo dõi mọi cuộc trao đổi với engineer.

📚

Git

Hệ thống lưu mọi phiên bản của code. Như máy thời gian: quay lại bất kỳ thời điểm nào trong quá khứ. Không bao giờ mất gì.

🌳

Main

Bản chính thức đang chạy thực tế cho user. Bất khả xâm phạm — không ai được sửa trực tiếp.

🌿

Branch (Nhánh)

Bản copy của dự án để làm việc riêng, không ảnh hưởng main. Mỗi feature = 1 branch.

🗂️

Worktree

Nhiều folder làm việc song song trên cùng 1 repo. Cho phép làm 2-3 feature cùng lúc không đụng nhau.

💾

Commit

1 mốc lưu trong quá trình code. Như save game — quay lại được bất cứ commit nào.

☁️

Push

Đẩy code từ máy lên server (GitHub). Trước push, code chỉ tồn tại trên máy bạn.

📝

Pull Request (PR)

Đề nghị merge branch vào main. Như nộp bản nháp cho biên tập viên duyệt.

🤖

CI

Robot tự động kiểm tra mỗi PR: test, format, security, kiến trúc. Cờ đỏ = không merge được.

2Pipeline đầy đủ — 4 giai đoạn

Đây là cách 1 feature đi từ ý tưởng tới user. Mỗi giai đoạn có vai trò riêng và "cửa kiểm soát" riêng.

1 SPEC
💡
  • Roadmap
  • Tracker
  • Phase plan
  • Feature spec (FE)
  • Tech spec (BE)
→
2 CODE
⚙️
  • Tạo branch
  • Tạo worktree
  • Viết code
  • Commit từng mốc
  • Push lên GitHub
  • Mở PR
→
3 REVIEW
🔍
  • CI tự động chạy
  • Cross-model review (Codex)
  • Sửa theo feedback
  • Push lại
  • Lặp tới khi xanh

4 SHIP
🚀

  • Dashboard rebuild
  • Branch xoá

Ghi nhớ:

Mỗi mũi tên giữa 2 giai đoạn là 1 cửa kiểm soát. Không qua được cửa thì không sang giai đoạn sau. CI và PR review chính là 2 cửa kiểm soát then chốt giữa CODE và SHIP.

3Worktree — chìa khoá làm song song

Cách 1 founder solo có thể chạy 3 cửa sổ Claude Code song song mà không phá nhau.

3 folder riêng biệt, 3 branch khác nhau, 3 session Claude Code chạy song song — nhưng cùng 1 kho dữ liệu Git phía sau.

Tại sao bắt buộc dùng worktree?

Trong project rule "STRICT 1 Claude Code session per .git/" được lock vì F07 saga đã có 3 sự cố ref-clobber — 2 session viết đồng thời vào cùng 1 .git/ làm refs (con trỏ branch) bị clobber, commit bị "mất" thành dangling.

Worktree giải quyết bằng cách cho mỗi session có 1 folder + 1 working tree riêng, nhưng vẫn share kho Git chung. Vừa parallel an toàn vừa không phải clone repo 2 lần.

43 Lane theo mức rủi ro

Không phải feature nào cũng dùng cùng 1 quy trình. Doc-only change ≠ multi-tenant DB migration.

🟢 Fast Lane

Cho thay đổi rủi ro thấp
  • Docs, config, cosmetic
  • Self-review cho phép
  • Spec optional
  • Max 2 round review
  • CI vẫn bắt buộc

🔵 Standard Lane

Cho feature thông thường (P1)
  • Spec FE + BE đầy đủ
  • Cross-model review bắt buộc
  • Max 5 round review
  • Manual merge sau approval
  • Test isolation bắt buộc nếu touch DB

🟣 Foundation Lane

Cho thay đổi kiến trúc (P0)
  • Spec chi tiết + ADR
  • Cross-model review + founder approval
  • Max 8 round (founder duyệt sau 5)
  • Không bao giờ auto-merge
  • Sign-off acceptance criteria trong PR body

5Thực tế — vòng lặp, không phải đường thẳng

Pipeline 4 giai đoạn nhìn tuyến tính, nhưng giai đoạn REVIEW thường lặp 2-8 lần trước khi qua được.

Mũi tên cam = forward path. Mũi tên đỏ đứt = quay lại sửa khi CI báo lỗi hoặc review request changes.

Ví dụ thực tế:

F07 saga mất 6 session mới merge xong. F01 mất 8 round review. Mỗi vòng = feedback báo lỗi → sửa code → push lại → CI chạy lại. Vì vậy CLAUDE.md đặt MAX_ROUNDS cap theo lane (Fast 2, Standard 5, Foundation 8) để không loop vô hạn.

65 quy tắc cứng quan trọng

Mỗi quy tắc dưới đây sinh ra từ 1 sự cố cụ thể trong quá khứ.

  1. 1. STRICT 1 Claude Code session per .git/ Mỗi folder Git chỉ 1 session ghi vào tại 1 thời điểm. Muốn parallel thì dùng worktree.
    Vết thương: F07 saga có 3 sự cố ref-clobber, commit bị "mất" vì 2 session viết cùng lúc.
  2. 2. NEVER auto-delete .md files Bất kỳ thao tác xoá file docs (checkout --theirs/ours, stash drop, rm) → PAUSE và hỏi founder trước.
    Vết thương: /md2html skill từng xoá file .md gốc sau khi convert.
  3. 3. Spec-first Không code trước khi đọc FE spec + BE tech spec. Tìm thấy gap → dừng và update spec.
    Code dựa trên giả định → tốn round review để sửa lại theo spec thật.
  4. 4. Tenant isolation test bắt buộc Bất kỳ feature nào động vào DB → bắt buộc có test multi-tenant. Không test → không merge.
    Multi-tenant + financial data: 1 lần leak data giữa user là không sửa được.
  5. 5. Cross-model review bắt buộc cho P1/P0 Claude Code viết → Codex review. Self-review chỉ cho phép ở Fast Lane.
    Self-review có blindspots; cross-model catch được lỗi architectural mà 1 model bỏ qua.

7Bảng tra cứu nhanh

Khi engineer dùng những từ này, đây là ý họ.

Thuật ngữ Ý nghĩa ngắn PM nghe trong câu nào?
Repo Repository — toàn bộ dự án + lịch sử "Tôi vừa pull repo mới nhất"
Main Nhánh chính, bản đang chạy production "Đã merge vào main chưa?"
Branch Nhánh làm việc riêng cho 1 feature "Tôi đang code trên branch funding-sources"
Worktree Folder thứ 2/3 cho parallel work "Mở worktree riêng cho feature này"
Commit 1 mốc save trong code "PR này gồm 5 commit"
Push Đẩy code local lên GitHub "Tôi vừa push thêm 1 commit"
Pull Tải code mới nhất từ GitHub về "Pull main về xem có gì mới"
PR Pull Request — đề nghị merge vào main "PR đã sẵn sàng review chưa?"
Squash-merge Gom tất cả commit branch thành 1 commit khi merge "Squash-merged vào main"
CI Robot kiểm tra tự động khi push/PR "CI đang fail, đợi tôi fix"
CI xanh / đỏ Pass / fail của robot kiểm tra "CI xanh rồi, mời anh review"
Review Người (hoặc AI) đọc code đề xuất sửa "PR còn 2 comment chưa resolve"
Merge conflict 2 branch sửa cùng 1 dòng, phải resolve tay "Có conflict với main, đang fix"
Rebase Sửa lịch sử branch để cập nhật theo main mới "Rebase trước khi merge"
Deploy Đưa code mới vào server cho user dùng "Đã auto-deploy sau merge"
Hotfix Fix khẩn cấp đi vòng quy trình thường để vào main nhanh "Cần hotfix bug sepay webhook"

8Cheat sheet cho PM

3 điều nhớ kỹ khi trao đổi với engineer:

  1. Main là bất khả xâm phạm Không ai sửa trực tiếp, mọi thay đổi đều qua PR. Khi engineer nói "merged chưa" — nghĩa là chỉ khi merged code mới đến tay user.
  2. Branch + Worktree = đường đa làn Nhiều feature làm song song không đè nhau. Đó là cách 1 founder solo có thể chạy nhiều việc cùng lúc.
  3. PR + CI = 2 cửa kiểm soát chất lượng PR là review của con người (hoặc Codex), CI là review của robot. Mọi thay đổi vào main đều qua cả 2 cửa. "PR đang chờ CI" = đợi robot; "PR đang chờ review" = đợi người.
